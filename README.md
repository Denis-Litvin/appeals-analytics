# Анализ обращений пользователей

Веб-сервис для поддержки клиентов интернет-магазина. Он хранит обращения пользователей, сам определяет категорию и причину по ключевым словам и показывает аналитику: статистику, частые причины, рейтинг проблем, сравнение периодов, графики, отчёты с выводами. При резком росте обращений по одной теме сервис присылает уведомление. Данные можно выгрузить в Excel и забрать через REST API.

Учебный проект VK Education. Коды требований (О1-О9, Д1-Д10, А1-А8, Р1-Р2) взяты из задания, их разбор лежит в [docs/requirements.md](docs/requirements.md).

## Стек

Python 3.10 или новее (проверено на 3.13), Django 5.2, Django REST framework, SQLite или PostgreSQL. Аналитика считается в pandas и numpy, графики строятся в Plotly, выгрузка в Excel идёт через openpyxl, словоформы обрабатывает snowballstemmer. Интерфейс собран на шаблонах Django без фронтенд-сборки. Полный список зависимостей в `requirements.txt`.

## Запуск

Создать и активировать виртуальное окружение:

```
python -m venv .venv
source .venv/bin/activate        # macOS и Linux
.venv\Scripts\activate           # Windows
```

Установить зависимости, подготовить демо-базу и запустить сервер:

```
pip install -r requirements.txt
python manage.py setup_demo
python manage.py runserver
```

`setup_demo` делает всё за один запуск:
1. применяет миграции;
2. загружает справочник категорий;
3. создаёт роли и демо-учётки;
4. генерирует 6000 обращений за полгода;
5. размечает всплески по всей истории.

На чистой базе это занимает 6-7 секунд. Если обращения уже есть, повторный запуск их не трогает. Пересоздать данные можно командой `python manage.py setup_demo --reset`.

Приложение откроется на http://127.0.0.1:8000/. Пароль у всех демо-учёток `demo12345`:

| Учётка | Роль | Что доступно |
|---|---|---|
| operator, operator2, operator3 | Оператор | обращения: просмотр, создание, правка, имена и email авторов |
| analyst | Аналитик | обращения без персональных данных, статистика, рейтинг, сравнение, дашборд, отчёты, выгрузка, уведомления |
| admin | Администратор | всё перечисленное, плюс справочники, правила и пользователи в /admin/ |

Как пользоваться интерфейсом в каждой роли, описано в [docs/user-guide.md](docs/user-guide.md).

## Демо-данные

Генератор создаёт правдоподобный поток обращений:
- будни загружены сильнее выходных, днём обращений больше, чем ночью, к концу периода поток растёт;
- в текстах есть опечатки, разговорная речь, обращения не по теме;
- на фиксированных днях заложены четыре всплеска.

Категорию каждому обращению ставит тот же классификатор, что работает в приложении. С заложенной причиной он совпадает примерно в 90% случаев, без категории остаются около 12% обращений. Подробности в [docs/demo-data.md](docs/demo-data.md).

## Команды

| Команда | Что делает |
|---|---|
| `setup_demo [--reset] [--count N] [--months M] [--seed S]` | готовит демо-базу одной командой |
| `load_dictionary [--prune]` | загружает категории, причины, ключевые фразы и теги из `appeals/data/dictionary.json` |
| `setup_roles [--demo-users]` | создаёт группы ролей с правами и демо-учётки |
| `generate_appeals [--count N] [--months M] [--seed S] [--clear]` | генерирует обращения и печатает сводку |
| `recategorize` | пересчитывает автокатегории по текущему словарю, ручные категории не трогает |
| `check_spikes [--from ГГГГ-ММ-ДД] [--to ГГГГ-ММ-ДД] [--notify]` | ищет резкий рост за дни (по умолчанию за сегодня), с `--notify` отправляет письмо аналитикам |
| `drf_create_token [-r] <логин>` | выдаёт токен API, с `-r` заменяет старый |

Новое обращение проверяется на всплеск сразу при сохранении, поэтому `check_spikes` нужен только для пересчёта за прошлые дни. Её можно поставить в cron раз в сутки, чтобы досчитывать дни, когда обращения загружались в базу пакетом.

## Настройки

Настройки задаются переменными окружения. Без них проект запускается в режиме разработки.

| Переменная | Значение по умолчанию | Зачем |
|---|---|---|
| `SECRET_KEY` | ключ для разработки | обязательно задать на сервере |
| `DEBUG` | `1` | на сервере `0` |
| `ALLOWED_HOSTS` | `localhost,127.0.0.1` | адреса сервера через запятую |
| `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_HOST`, `POSTGRES_PORT` | не заданы | если задан `POSTGRES_DB`, вместо SQLite используется PostgreSQL. Нужен драйвер: `pip install "psycopg[binary]"` |
| `EMAIL_BACKEND` | вывод писем в консоль | для настоящей почты `django.core.mail.backends.smtp.EmailBackend` |
| `EMAIL_HOST`, `EMAIL_PORT`, `EMAIL_HOST_USER`, `EMAIL_HOST_PASSWORD`, `EMAIL_USE_TLS` | `localhost`, `25`, пусто, пусто, `0` | параметры SMTP |
| `DEFAULT_FROM_EMAIL` | `appeals@example.com` | адрес отправителя писем о всплесках |

Письма о всплесках получают активные пользователи с правом на аналитику, у которых заполнен email. Демо-учёткам email выдан вида `analyst@example.com`.

## Ограничения

Автокатегория работает по словарю, поэтому:
- опечатка в первой букве слова не распознаётся: «Курер не приехал» получит категорию «Доставка», а «Гурьер не приехал» останется без категории;
- если две категории набрали почти одинаково (меньше чем в полтора раза разницы), обращение остаётся без категории;
- слова с общим началом основы иногда совпадают: жалоба «это отписка какая-то, а не ответ» попадает в причину «Уведомления и рассылки»;
- вежливые концовки вроде «жду ответа» добавляют баллы причине «Долгий ответ поддержки»: «Не пришёл заказ. Жду ответа» уходит в «Обслуживание».

Новые формулировки добавляются в справочник через админку, после этого команда `recategorize` пересчитывает старые обращения.

Поиск по тексту:
- ищет по началу основы слова;
- не исправляет опечатки в запросе;
- не связывает формы с разной основой: «проходит» не найдёт «прошли»;
- поиск по email работает только при наличии в строке символа «@».

Поиск резкого роста:
- в первые две недели данных не срабатывает, потому что нужна история;
- кроме заложенных всплесков находит и случайные выбросы генератора: в замере на демо-базе за полгода их было 4 по категориям и 3 по причинам.

Выгрузка и графики:
- выгрузка собирается в памяти целиком: 6000 обращений готовятся за 1-2 секунды, для сотен тысяч строк нужна потоковая отдача;
- файл plotly.js весит 4,8 МБ и кэшируется браузером на год, но сам сервис его не сжимает. На сервере сжатие стоит включить в веб-сервере (gzip в nginx);
- печатная версия отчёта рассчитана на A4 в Chrome и Safari, графики перед печатью перестраиваются под ширину листа.

API:
- токены не истекают сами, их заменяют командой `drf_create_token -r`;
- частота запросов не ограничена.

Запуск рассчитан на `runserver` и SQLite. Для работы на сервере нужны PostgreSQL, `DEBUG=0`, свой `SECRET_KEY`, `collectstatic` и отдача статики веб-сервером. Эти настройки в проект не входят.
