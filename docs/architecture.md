# Архитектура

Проект на Django из трёх приложений. Страницы собираются на сервере шаблонами Django. JavaScript нужен только для графиков Plotly и двух мелочей в формах: фильтра причин по категории и переключения варианта сравнения.

## Приложения

| Приложение | За что отвечает | Главные файлы |
|---|---|---|
| `appeals` | обращения, справочники, роли, автокатегория, поиск и фильтры, страницы оператора, генератор демо-данных | `models.py`, `classify.py`, `text.py`, `filters.py`, `roles.py`, `views.py` |
| `analytics` | статистика, сравнение, рейтинг, поиск всплесков, графики, отчёт, выгрузка, страницы аналитика | `stats.py`, `spikes.py`, `charts.py`, `reports.py`, `export.py`, `views.py` |
| `api` | REST API поверх тех же функций | `views.py`, `serializers.py`, `permissions.py` |

`config` хранит настройки и корневые адреса. Зависимости идут в одну сторону: `api` использует `analytics` и `appeals`, `analytics` использует `appeals`. Исключение одно: страница создания обращения в `appeals` вызывает проверку всплеска из `analytics.spikes` и выгрузку из `analytics.export`.

## Данные

Схема описана в [database.md](database.md). Коротко:
- `Category` и `Reason` образуют двухуровневый справочник;
- `KeywordRule` хранит ключевые фразы с весами для причин;
- `Tag` хранит свободные метки;
- `Appeal` хранит обращение;
- `SpikeAlert` хранит уведомление о росте.

У обращения не больше одной категории и одной причины. Причина без категории запрещена ограничением в базе.

Поле `Appeal.text_norm` хранит основы слов текста и темы через пробел. Оно заполняется при сохранении и используется в поиске. Там же при сохранении определяется категория, если текст новый или изменился, а категорию не ставили вручную.

## Как проходит запрос аналитика

1. Форма периода (`analytics/forms.py`) проверяет параметры. Без дат берутся последние 30 дней, неверное значение заменяется значением по умолчанию.
2. `apply_filters` из `appeals/filters.py` строит запрос к базе. Это та же функция, что фильтрует список обращений, поэтому фильтры работают одинаково везде.
3. `stats.load_frame` забирает нужные поля одним запросом в DataFrame pandas и переводит время в московское.
4. Функции `stats.py` считают сводку, разбивки, топ причин, рейтинг, сравнение, таблицу по дням.
5. Из этих же строк строятся графики (`charts.py`), отчёт с выводами (`reports.py`), выгрузка (`export.py`) и ответы API (`api/views.py`).

Таблица, график, отчёт, файл выгрузки и API берут числа из одного источника и разойтись не могут. Тесты проверяют это совпадение: числа pandas сверяются с подсчётами в базе, графики с таблицами, API со страницами.

Считать в pandas, а не агрегатами базы, решено ради простоты. Выборка за год укладывается в несколько десятков тысяч строк, и такой расчёт идёт быстрее, чем много отдельных запросов. На демо-базе из 6000 обращений страница статистики собирается за 10-70 мс.

## Автокатегория

`appeals/classify.py` работает так:

1. Текст приводится к нижнему регистру, «ё» заменяется на «е», слова режутся до основы стеммером Snowball (`text.py`).
2. Для каждой ключевой фразы ищутся её основы в тексте. Слова фразы могут стоять в любом порядке, но в пределах окна «число слов фразы + 2». Если в фразе есть «не», оно должно стоять прямо перед своим словом.
3. Допускается одна опечатка: пропуск, лишняя буква, замена или перестановка соседних. Первая буква должна совпадать. Опечатка ищется в словах от 5 букв, а разные формы одного слова сравниваются по основам от 6 букв.
4. Веса сработавших фраз (1-3) складываются по причинам и категориям.
5. Категория ставится, если у неё не меньше 2 баллов и она опережает следующую категорию в полтора раза. Иначе обращение остаётся без категории.
6. Внутри категории выбирается причина с наибольшим баллом.

Сработавшие фразы сохраняются в `category_matches`, карточка обращения показывает их и подсвечивает слова в тексте. Точность классификатора:
- на размеченном наборе из тестов 55 текстов из 55;
- на сгенерированных демо-данных около 90% совпадений с заложенной причиной.

## Поиск

`text_query` в `appeals/filters.py` разбирает строку поиска:
- `#1234` ищет по номеру обращения;
- строка с «@» ищет по email автора, если пользователю показывают email. У аналитика она ищется как обычный текст, иначе по поиску можно было бы проверить, писал ли конкретный адрес;
- фраза в кавычках ищется как идущие подряд основы;
- остальные слова ищутся каждое по началу основы в `text_norm`, все условия соединяются через И, служебные слова пропускаются.

## Поиск всплесков

`analytics/spikes.py` считает обращения по дням для каждой категории и каждой причины. Обычный уровень дня берётся как медиана за 28 предыдущих дней, умноженная на коэффициент дня недели. Разброс оценивается как медиана отклонений, умноженная на 1,4826. День считается всплеском, если выполнены три условия сразу:
- обращений не меньше чем вдвое больше обычного;
- превышение не меньше 8 для категории и 5 для причины;
- (число − обычный уровень) / (разброс + 1) не меньше 3.

Для сегодняшнего незаконченного дня обычный уровень уменьшается пропорционально доле суточного потока, которая обычно приходит к этому часу. Дни до первого обращения в базе в историю не входят.

Проверка запускается после каждого нового обращения, но только для его категории и причины за сегодня. Дополнительно её запускают команда `check_spikes` и `setup_demo`. На один день и одну цель приходится одно уведомление: повторная проверка обновляет число, а письмо уходит только о новых уведомлениях. Прочитанность хранится отдельно у каждого пользователя.

Медиана и MAD выбраны вместо среднего и стандартного отклонения, потому что прошлые всплески не должны поднимать порог для следующих. На демо-данных находятся все заложенные всплески, проверка по всей полугодовой истории занимает меньше секунды.

## Графики

`charts.py` строит фигуры Plotly на сервере и передаёт их в шаблон как JSON. `static/js/charts.js` рисует их и на клике переходит по ссылке, которая лежит в данных точки. Так клик по столбцу открывает список обращений с тем же периодом и фильтрами.

Файл plotly.js отдаётся из Python-пакета plotly по адресу с номером версии и кэшируется на год. Внешних адресов на страницах нет, поэтому графики работают без интернета. Русская локаль Plotly (месяцы, подсказки панели) задана в `charts.js`.

## Отчёт и выгрузка

`reports.build` собирает все данные отчёта за период. Выводы текстом (`reports.conclusions`) строятся правилами из тех же чисел. Рост категории попадает в выводы, только если изменение заметное: не меньше 20% и не меньше 10 обращений разницы.

Печатная версия задаётся отдельной таблицей стилей `print.css`: меню, фильтры и кнопки скрываются.

`export.py` пишет тот же отчёт в XLSX по листу на раздел или один раздел в CSV (UTF-8 с BOM, разделитель «;»). Текст, который начинается с «=», «+», «-» или «@», получает апостроф, чтобы Excel не принял его за формулу.

## Права

Роли сделаны группами Django с наборами прав (`appeals/roles.py`). Свои права:
- `view_personal_data`: видеть имя и email автора;
- `view_analytics`: смотреть статистику и уведомления;
- `export_reports`: выгружать;
- `manage_dictionary`: вести справочник.

Весь сайт закрыт входом через `LoginRequiredMiddleware`. Каждая страница дополнительно проверяет своё право и отвечает 403 со страницей «Нет доступа».

Имя и email автора проходят через одну функцию `author_for`. Она отдаёт полные данные пользователю с `view_personal_data`, остальным маску вида «И*** П***», «i***@mail.ru». Через неё идут карточка, выгрузка и API.

API проверяет токен DRF и те же права (`api/permissions.py`). Без токена ответ 401, без права 403. Тест `tests/test_access_matrix.py` проходит по всем адресам проекта для четырёх ролей.

## Принятые решения

| Решение | Почему |
|---|---|
| Django и шаблоны вместо отдельного фронтенда | меньше движущихся частей, все страницы работают без сборки |
| SQLite по умолчанию, PostgreSQL одной переменной | запуск одной командой на любой машине. Поиск по `text_norm` через LIKE работает в обеих базах |
| Классификатор по словарю, а не модель машинного обучения | нет размеченных данных для обучения. Правила понятны: в карточке видно, почему выбрана категория, а администратор правит словарь без программиста |
| Основы Snowball вместо полной морфологии | одна лёгкая зависимость. Ошибки стеммера на кратких формах закрыты сравнением по началу основы |
| Медиана и MAD для всплесков | устойчивы к прошлым всплескам и выходным |
| Фигуры Plotly на сервере | числа графика берутся из тех же функций, что таблица, и проверяются тестами без браузера |
| Роли через группы и права Django | права работают одинаково на сайте, в админке и в API |
