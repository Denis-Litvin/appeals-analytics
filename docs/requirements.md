# Анализ требований

Документ фиксирует, как я понимаю задание «Анализ обращений пользователей» и какие решения принял там, где задание допускает разные трактовки. Коды требований те же, что в задании: О1-О9 обязательная функциональность, Д1-Д10 дополнительная, А1-А8 этапы, Р1-Р2 результат.

## Предметная область

Для демо-данных взят условный маркетплейс с мобильным приложением, онлайн-оплатой и доставкой. Обращения в такой сервис разнородные: оплата и списания, доставка и заказы, возвраты, вход в аккаунт, ошибки приложения, промокоды, качество товара. Этого хватает, чтобы на данных были видны и устойчивые частые причины, и всплески.

Приложение внутреннее. Им пользуются сотрудники поддержки и аналитики, авторы обращений в систему не входят.

## Роли и сценарии

Оператор поддержки разбирает поток обращений. Он ищет и открывает обращения, исправляет категорию, ставит теги, меняет статус, заносит обращение, принятое по телефону.

Аналитик смотрит дашборд и рейтинг проблем, сравнивает периоды, выгружает отчёты, получает уведомления о всплесках, забирает данные через API. Имя и email автора ему для этого не нужны, поэтому у него они маскируются.

Администратор ведёт справочники категорий, причин, ключевых фраз и тегов, управляет пользователями, запускает пересчёт автокатегорий. У него есть все права двух других ролей.

| Действие | Оператор | Аналитик | Администратор |
|---|---|---|---|
| Список и карточка обращений | да | да | да |
| Имя и email автора | видит | скрыты | видит |
| Создание, правка, категория, теги | да | нет | да |
| Статистика, рейтинг, сравнение, дашборд | нет | да | да |
| Отчёты и выгрузка | нет | да | да |
| Уведомления о всплесках | нет | да | да |
| API | обращения: чтение и создание | статистика и обращения на чтение | всё |
| Справочники, правила, пользователи | нет | нет | да |

## Неоднозначности и принятые решения

«Различные категории пользователей» в Д10 понимаю как роли сотрудников. Клиенты в системе не авторизуются.

В О5 речь о категориях, в О7 о причинах, в Д7 о проблемах. Справочник двухуровневый: категория описывает крупную область (около 8 штук), причина описывает конкретную проблему внутри неё (около 30). О7 показывает топ по обоим уровням, Д7 строит рейтинг по причинам.

Категория у обращения одна, поэтому доли в статистике складываются в 100%. Теги описывают другие измерения (платформа, повторность, важность клиента), и их может быть несколько.

Если автокатегоризация не уверена, обращение остаётся без категории. В статистике у таких обращений своя строка «Без категории», в фильтре свой пункт. Доля таких обращений показывает, насколько полон словарь.

Ручная категория приоритетнее автоматической. Пересчёт по словарю её не перезаписывает.

Реального потока данных в задании нет. Обращения попадают в систему через форму, через API и из генератора. Импорт из файла не делаю: в задании его нет, приём из внешних систем закрывает API.

Формат отчёта в задании не задан. Отчёт делается HTML-страницей с печатной версией, к ней выгрузка в XLSX и CSV.

«Резкий рост» в Д8 определяю так. Для каждой категории и причины считается число обращений в сутки. Базой служит медиана за предыдущие 28 дней, разбросом служит MAD × 1,4826. День считается всплеском, если число не меньше двух медиан, превышение над медианой не меньше 8 для категории (5 для причины) и (число − медиана) / (разброс + 1) ≥ 3. Для текущего, ещё не закончившегося дня база уменьшается пропорционально доле суток, которая обычно приходится на прошедшие часы.

Часовой пояс приложения Europe/Moscow. Время хранится в UTC, сутки для статистики считаются по Москве.

Объём рассчитан на десятки тысяч обращений. SQLite с индексами на таком объёме отвечает быстро, для большей нагрузки проект переключается на PostgreSQL без изменения кода.

## Известные ограничения

Автокатегоризация работает по словарю и не понимает контекст. В тексте «оплата прошла нормально, но курьер не приехал» совпадут фразы двух категорий, и выбор сделает сумма весов.

Поиск идёт по основам слов, которые даёт стеммер Snowball. Опечатки в запросе не исправляются. Формы с разной основой («приходит» и «пришла») стеммер к одной основе не сводит, такие слова находятся только по своим формам.
